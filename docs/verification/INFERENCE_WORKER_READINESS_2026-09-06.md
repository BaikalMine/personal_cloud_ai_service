# Готовность и запуск inference-worker

## Реализовано

- У отдельного исполнителя есть `GET /healthz`: протокол 2, имя сервиса,
  булево `ready`. Ответ не содержит запросов, токенов, адресов БД и ID пользователей.
- Готовность требует работающего цикла обработки и доступной БД. Длительный
  запрос модели сам по себе не делает процесс неготовым. После выхода из цикла
  готовность снимается; до успешного первого обслуживания БД и восстановления
  постоянного журнала она не объявляется. [Дополнение и проверки журнала](INFERENCE_OUTCOME_RECOVERY_2026-09-06.md).
- HTTP-проверка ограничена двумя секундами. Если драйвер задерживает отмену,
  следующие проверки разделяют один незавершённый probe, не создавая новые
  зависшие SQL-вызовы. Недоступность возвращает 503, а не ложный 200.
- Gateway показывает «Исполнитель ассистентов» в существующем мониторинге при
  включённом постоянном режиме хотя бы одного ассистента. Проверяются имя сервиса,
  версия протокола и `ready`, а не только HTTP 200. Redirect не принимается.
- `INFERENCE_WORKER_URL` по умолчанию: `http://inference-worker:8096`.
  Сам процесс без настройки слушает только `127.0.0.1:8096`; Compose задаёт
  внутренний listener `:8096`, без публикации порта на хост.
- Dockerfile имеет отдельную цель `inference-worker`. Последняя, стандартная
  цель остаётся Gateway. Оба образа работают как `appuser`.
- Добавлен опциональный `docker-compose.inference.yml`; основной Compose не
  запускает нового исполнителя автоматически. Ему передаются только DSN,
  content cipher secret, адрес Ollama и настройки самого процесса.
- Артефакты браузерных тестов исключены из Docker build context.

## Приёмка

1. Полный Go-прогон с отдельной PostgreSQL 16 на tmpfs выполнен дважды успешно,
   включая новый конкурентный тест восьми health-запросов при зависшем драйвере,
   проверку длительного inference и остановки цикла без освобождения GPU.
2. Проверены неверный протокол, другой сервис, HTML вместо JSON, лишний JSON,
   redirect, 503, запрещённые методы, HEAD, отсутствие конфигурации и отдельное
   включение мониторинга для captions и генерационного ассистента.
3. Собраны Docker-цели Gateway и inference-worker; проверены их разные entrypoint
   и непривилегированный пользователь. Исправленный worker пересобран повторно.
4. Compose проверен командой `docker compose --env-file .env.example -f
   docker-compose.yml -f docker-compose.inference.yml config --no-env-resolution
   --quiet`. Реальный `.env` не использовался.
5. Собранный worker запущен на пустой тестовой БД с адресом модели
   `http://127.0.0.1:1`. Начальная готовность: 200/ready=true.
6. Приостановка тестовой PostgreSQL сначала выявила зависание отмены в драйвере.
   После исправления и пересборки тот же сценарий дал HTTP 503 за ~2 секунды.
   После возобновления БД снова получен ready=true без перезапуска worker.

Production, рабочий ComfyUI, Ollama, майнинг и Windows-agent не изменялись.
UI-шаблоны и стили не менялись; отдельная браузерная приёмка этого этапа не проводилась.

## Порядок будущего выпуска

Это инструкция для согласованного F14, не разрешение обновлять работающие GPU-процессы.

1. Проверить backup/restore, отсутствие неизвестных отправок и совместимость
   Gateway, новой схемы (миграция 65) и Windows-agent. Не прерывать текущую работу.
2. Выпустить проверенный Gateway с выключенными `LORA_CAPTION_DURABLE_INFERENCE`
   и `PROMPT_ASSISTANT_DURABLE_JOBS`. Выполнить release smoke и проверить миграции.
3. Собрать отдельную цель и запустить только `inference-worker` с этим overlay.
   Worker использует ту же БД, `SESSION_SECRET` и `OLLAMA_UPSTREAM`, что Gateway.
   Обязателен постоянный том `INFERENCE_OUTCOME_DIR` и проверенный порядок его
   backup/restore вместе с БД. Протокол 1 без журнала больше не принимается.
4. Проверить здоровье контейнера и сетевую доступность его healthz из Gateway.
   Сам healthz не проверяет качество модели, доступность её весов или освобождение GPU.
5. Только после общей приёмки включать постоянные режимы. Перед заменой/остановкой
   worker дождаться подтверждённого завершения отправленных задач.

## Остаток

Это закрывает подготовку запуска и базовый мониторинг исполнителя, не весь F04/F14.
Healthz не является доказательством завершения неизвестного модельного вызова и
никогда не освобождает GPU или mining lease. Подтверждение со стороны модели,
внешние задачи, поздний запуск майнера, смешанная нагрузка, эксплуатационный журнал,
версии компонентов, полноценный rollback и production rollout остаются открытыми.
