# F04: основа общего допуска к GPU

Статус: серверная основа проверена локально; F04 целиком не завершён.
Рабочие обработчики запуска и production пока не переключены на новый допуск.
Миграция 56 добавляет таблицы, но сама по себе не меняет планирование задач.

## Что реализовано

- Один ресурс `primary` для текущего GPU и четыре типа работы: generation,
  lora_training, lora_caption, prompt_assistant. Различные жизненные циклы
  исходных задач сохраняются, общий реестр отвечает только за ресурс.
- Один владелец в состояниях `held` или `uncertain`, обеспеченный блокировкой
  ресурса в транзакции и уникальным частичным индексом PostgreSQL.
- Приоритет даёт преимущество в 10 минут виртуального времени ожидания.
  Давно ожидающая обычная работа проходит перед новой приоритетной;
  уже запущенная работа не вытесняется. Значение пока является серверной
  константой, миграция пользовательской политики ещё не выполнена.
- Короткоживущий запрос на допуск обновляется отдельно от времени постановки
  в очередь. Необновлённые, отменённые, заблокированные и истёкшие владельцы
  не получают новое место; удаление пользователя не освобождает активный GPU.
- Перед сетевой отправкой обязательна фаза `dispatching`. Потерянный ответ
  нельзя считать доказательством, что запрос не был принят исполнителем.
- Истечение lease переводит владение в `uncertain` при следующей попытке
  допуска. Ресурс остаётся занят. Просроченный heartbeat не возрождает lease.
- Для освобождения нужны соответствующий токен и актуальная версия ресурса.
  Для завершённого синхронного ответа и отмены до отправки дополнительно
  проверяются срок владения и фаза, даже если другой worker ещё не заметил TTL.
- Наблюдение исполнителей публикуется с версией, полученной ДО проверки.
  Поздний ответ `idle` не перезаписывает новую выдачу, отправку или освобождение.
  После освобождения следующему владельцу нужна новая проверка исполнителей.
- Переходы и основание освобождения записываются в `gpu_work_events`.

## Поиск принятого обучения

Добавлен авторизованный read-only API агента:
`GET /v1/gateway-jobs?gateway_job_id=...`.

Он возвращает обычный `JobStatus` по исходному ID Gateway, включая queued,
active и terminal записи. Это позволит восстановить связь с заданием после
потери ответа `Submit`, не создавая ещё одну отправку. Клиент проверяет оба ID;
старый агент, HTTP-ошибка, отсутствие записи или некорректный ответ не
преобразуются в успешное завершение. Gateway dispatcher пока этот API не вызывает.

Важно: наличие terminal записи не является новым подтверждением отсутствия
процесса после аварийного перезапуска агента. Существующий `loadJobs` помечает
старые незавершённые записи failed; это нельзя использовать как единственное
основание освобождения GPU. Нужна проверка реального исполнителя.

## Проверки

Проверено в отдельной tmpfs PostgreSQL 16, без production-данных и запусков GPU:

- `go test -p 1 -count=1 -timeout=180s ./...`: успешно.
- database/store/gateway с `TEST_DATABASE_URL`, без кеша тестовых результатов:
  успешно; проверены реальные миграции и существующие интеграционные сценарии.
- `TestGPUAdmissionIntegration`, 10 повторов: успешно. Каждый повтор содержит
  32 конкурентные попытки через независимые экземпляры Store и четыре вида
  работ; допуск получила ровно одна работа.
- Приоритет и aging, поздняя/просроченная проверка idle, cancel активной работы,
  TTL, новый экземпляр Store после потери владельца, удаление пользователя,
  новое владение при retry, старые токены и журнал событий: успешно.
- Отдельно проверен TTL при освобождении ДО попытки другого worker,
  чтобы безопасность не зависела от частоты сверки очереди.
- HTTP-контракт поиска обучения: все состояния, авторизация, GET-only,
  код `job_not_found`, восстановление индекса из сохранённых записей,
  непрозрачные ID, старый агент, 503, неверный JSON и несовпадение ID: успешно.

Это тесты контракта и конкурентного доступа к БД. Fixtures `busy`, `idle` и
`executor_terminal` не являются реальным измерением ComfyUI или VRAM.
Новые UI-тесты не запускались: frontend в этом изменении не менялся.

## Остаток F04

1. Подключить генерацию, пакеты, обучение, captions и prompt-assistant к
   сохранённому допуску. Сохранять все ожидающие intents, а не только первого
   кандидата каждого worker, чтобы приоритет отражал всю очередь.
2. Сделать совместимую миграцию: отдельный пользовательский приоритет и
   политика остановки майнинга. Привязать mining lease к GPU work, исключить
   освобождение долгого assistant/caption по нынешнему таймеру в две минуты.
3. Реализовать адаптеры наблюдения/сверки ComfyUI, агента обучения и inference.
   Проверить неизвестные внешние работы, потерю ответа и перезапуск процесса.
   SQL-допуск сам по себе не сериализует прямые запуски вне Gateway;
   обычная проверка `/queue` перед отправкой не устраняет эту гонку.
4. Подключить восстановление принятого обучения через новый lookup API.
   Отсутствие записи и сетевой таймаут должны сохранять неопределённость.
5. Обновлять heartbeat, обрабатывать cancellation и готовность ожидающих
   задач, очищать завершённые записи по согласованной retention-политике.
6. Показать в UI реальную причину ожидания и позицию, не фальшивый процент.
7. Измерить смешанную нагрузку и память на реальных профилях; проверить
   видео + LoRA + caption, отмену пакета, восстановление Gateway/агента,
   недоступный агент и сторонний ComfyUI. Майнер запускается только после
   освобождения последнего владельца и подтверждения завершения исполнителей.

До выполнения этих пунктов F04 не считается готовым и не включается в production.
