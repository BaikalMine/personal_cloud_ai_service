# Восстановление наблюдённого результата inference

## Область

Часть F04: модель уже вернула окончательный ответ, но транзакция результата
в PostgreSQL не прошла и процесс исполнителя аварийно завершился.
Это не доказательство завершения запроса, ответ которого никто не получил.

## Реализовано

- Перед транзакцией результата исполнитель сохраняет шифрованное подтверждение
  в постоянном каталоге `INFERENCE_OUTCOME_DIR`. Запись: временный файл,
  `Sync`, закрытие, замена. Имя содержит только хеш ID; содержимое, включая
  токены привязки, защищено существующим content cipher и AAD имени файла.
- После рестарта подтверждения обрабатываются до допуска новой работы.
  Проверяются ID, постоянный run token, GPU lease, hash запроса и время наблюдения.
  Результат и подтверждение GPU записываются одной транзакцией. Файл удаляется
  только после её успеха. Повторная обработка уже записанного подтверждения
  не повторяет запрос модели и не изменяет срок хранения.
- Отмена пользователя не уничтожает доказательство фактически завершённой работы.
  Флаг отмены сохраняется; потребитель по-прежнему применяет свой контракт отмены.
- Срок хранения ответа: 24 часа от первоначального наблюдения, не от рестарта.
  При обработке просроченного файла тело удаляется даже перед повторной попыткой
  записи в недоступную БД; минимальное подтверждение остаётся до согласования.
- Повреждённый файл, неверная привязка или недоступный каталог останавливают
  новый dispatch и снимают readiness. Неизвестный исход не превращается в успех.
- Readiness теперь использует протокол 2. До первоначального восстановления
  журнала worker не готов. Gateway не принимает старый протокол 1.
- Compose overlay монтирует отдельный `inference-outcomes`; нативный запуск
  требует абсолютный постоянный каталог. Эфемерный `/tmp` не подходит.

## Проверки

- Полный Go-прогон с изолированной PostgreSQL 16 прошёл; новые сценарии
  outcome/readiness повторены десять раз без ошибок. `go vet ./...` прошёл.
- Реальный дочерний тестовый процесс был принудительно завершён после записи
  файла, пока SQL trigger запрещал фиксацию результата. Новый worker восстановил
  тот же ответ по тому же ID; счётчик вызовов синтетической модели остался равен 1.
- Проверены отмена, повторное подтверждение после commit, истечение 24 часов
  при отказе БД, неверные run token/hash/lease, HTTP 504 и недоступный журнал.
- Проверены шифрование, подмена содержимого/имени, неверный ключ, границы размера,
  абсолютный каталог и symlink. Последний сценарий прошёл в Linux; в Windows
  пропущен из-за отсутствия привилегии создания symlink.
- Нативные Windows-тесты записи, замены, расшифровки и ошибок каталога прошли.
  Интеграционный Windows-тест без `TEST_DATABASE_URL` штатно пропущен; БД-сценарии
  выполнены в Linux-контейнере, не выдаются за Windows-интеграцию.
- Собран отдельный образ `ai-gateway-inference-outcomes-test:20260906`.
  Проверен read-only контейнер с постоянным томом (владелец UID 10001):
  `healthz` вернул `protocol:2, ready:true`. Адрес модели был `127.0.0.1:1`.
  Compose проверен через `.env.example`, без чтения рабочего `.env`.

## Эксплуатационные ограничения

- Один каталог принадлежит одной паре БД/ключа. При замене контейнера нужно
  сохранять том; `down -v`, очистка каталога и удаление неизвестных подтверждений
  не являются способом починки очереди. Несогласованные файлы требуют разбора.
- Штатный backup датасетов/LoRA пока не включает этот новый том. До включения
  режима в production F14 обязан добавить согласованный backup/restore журнала
  вместе с БД и проверку отсутствия повторного исполнения. Старый backup нельзя
  объявлять полным disaster recovery постоянного исполнителя.
- Очистка просроченного тела выполняется работающим worker. Пока он выключен,
  файлы не чистятся внешним таймером. Сроки архивных копий задаются отдельно.
- На Windows `File.Sync` и замена проверены для рестарта процесса. Гарантия
  сохранения после потери питания не заявляется: directory fsync недоступен.
- Повреждённое/недописанное временное содержимое не становится подтверждением.
  Остатки временных файлов не удаляются массово; лимит каталога блокирует новые
  отправки и требует диагностики, а не скрытой потери доказательств.
- Окно между получением ответа и успешной записью файла полностью не устранено.
  Сбой во время самого вызова модели остаётся неизвестным: необходим контракт
  подтверждения со стороны исполнителя модели. Healthz, время и пустой список
  загруженных моделей не разрешают освобождение GPU.
