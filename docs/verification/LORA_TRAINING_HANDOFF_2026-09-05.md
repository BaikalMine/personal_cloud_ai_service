# F04: устойчивая передача обучения

Статус: подключено к рабочим обработчикам, проверено локально; не развёрнуто.
Это часть F04, а не завершённая общая очередь GPU.

## Изменения

- Миграция 57 добавляет `agent_submission_started_at`. Маркер записывается
  перед сетевым Submit. Существующие uploading-записи без agent ID при
  миграции считаются потенциально отправленными, а не гарантированно пустыми.
- После HTTP-ошибки или потери ответа job остаётся uploading, сохраняя датасет
  и mining lease. Обычный requeue и восстановление после рестарта Gateway не
  могут объявить такую работу отменённой или автоматически отправить её ещё раз.
- Worker ищет принятую работу по исходному Gateway ID, привязывает agent ID
  и продолжает обычное наблюдение. Повторная отправка датасета не требуется.
- Если агент подтвердил отсутствие записи, Gateway сначала закрывает путь
  запоздалой отправки: POST `/v1/gateway-jobs/fence?gateway_job_id=...`.
  Только подтверждённые `fenced` и `settled` позволяют освободить ресурсы.
- Агент сохраняет fence на диске перед ответом. Проверка выполняется до и
  после загрузки датасета. Уже начатая, но ещё не зарегистрированная загрузка
  не попадёт в очередь после fence. Новое обучение использует новый Gateway ID.
- Fence не удаляется вместе с карточкой и загружается после перезапуска.
  Это небольшая служебная запись, не кэш. Её нельзя очищать вместе с датасетами.
- При найденной queued-задаче агент отменяет её до запуска; при активном
  процессе подтверждение остаётся unsettled до фактического завершения.
- Перезапуск агента больше не выдаётся за доказанную остановку старого
  процесса. Такие записи имеют `execution_unconfirmed`; Gateway сохраняет
  последнее подтверждённое состояние и паузу майнинга. Неизвестный статус
  также не превращается автоматически в failed.
- Записи с неподтверждённым завершением процесса не удаляются ни вручную через
  API агента, ни обычной очисткой failed-истории. Подтверждённые ошибки по-прежнему
  удаляются через сутки. Это защита потенциально активной работы, не отмена retention.
- Claim обучения сериализован в PostgreSQL: новое обучение не передаётся
  агенту, пока существует uploading/preparing/caching/running/installing.
  Общая координация с генерациями и ассистентами пока не подключена.

## Проверки

Использована отдельная tmpfs PostgreSQL 16 без внешних портов. Рабочие сервисы,
пользовательские файлы, ComfyUI и GPU не использовались для тестовых запусков.

- Полный `go test -p 1 -count=1 -timeout=180s ./...` с `TEST_DATABASE_URL`:
  успешно, включая реальные миграции и существующие интеграционные тесты.
- 13 сценариев handoff: потеря ответа Submit, новый экземпляр App,
  недоступный/старый агент, неизвестный статус, неподтверждённый процесс,
  уже привязанный неподтверждённый процесс, отмена ещё работающей задачи,
  подтверждённый fence, отмена до подтверждения, завершение между lookup и
  fence, неполное и некорректное подтверждение.
- Проверено: не теряются датасет и mining lease до подтверждения; новая
  отправка не создаётся; завершившаяся между проверками работа сохраняет
  agent ID и ссылку на скачиваемый артефакт.
- Тест агента с заблокированным `io.Pipe` воспроизводит настоящий in-flight
  upload: fence уже подтверждён, затем передача продолжается, но в очередь
  работа не попадает. Этот и остальные `TestSubmissionFence*` повторены 10 раз.
- Проверены reload fence, удаление карточки, отмена работающей задачи,
  restart uncertainty, невозможность удалить неподтверждённый процесс,
  ошибка сохранения fence, HTTP client/server и отклонение ложных подтверждений.
- После восстановления прерванного редактирования отдельно добавлен тест
  повреждённого execution inventory: нечитаемый JSON и несогласованный ID
  не игнорируются как отсутствие задач. Полный прогон повторён успешно.
- Windows amd64 агент собран через `GOOS=windows GOARCH=amd64 CGO_ENABLED=0`.
  Windows-бинарник не запускался и не устанавливался.

## Выпуск и остаток

Нужен согласованный выпуск Gateway и агента обучения. Старый агент без lookup
или fence API не подтверждает неопределённую передачу; Gateway сохраняет её
ожидание вместо рискованного повторного запуска. Перед обновлением проверить
активные работы; текущий пользовательский процесс ComfyUI не перезапускать.

Нельзя откатывать Gateway на версию, которая не учитывает маркер отправки,
при наличии неопределённых handoff-записей. Сначала завершить их сверку.

Следующие обязательные части F04: фактическая проверка процессов после
аварийного рестарта агента; привязка к общему GPU lease; совместный допуск
генерации/обучения/caption/assistant; разделение приоритета и mining policy;
внешние задачи ComfyUI; реальная смешанная нагрузка и UI ожидания. Текущие
тесты HTTP/БД не доказывают остановку реального дерева Python-процессов.
