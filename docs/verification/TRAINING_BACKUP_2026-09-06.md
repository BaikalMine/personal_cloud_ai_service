# F05: архив обученных LoRA

Дата: 2026-09-06. Статус: сквозная локальная приёмка; rollout не выполнен.

## Реализовано

- `cmd/training-backup`: потоковый ZIP export/restore без запуска GPU-сервисов.
- `Trained` и завершённые status records, SHA-256, owner/run/profile linkage.
- Новые Submit сохраняют снимок профиля; legacy records получают предупреждение.
- Кеши, частичные установки и базовые веса исключены из архива. Для базовых
  моделей сохранён отдельный inventory/hash/recovery; недоступные пути видны.
- Сохранённые датасеты и подписи включаются политикой `database` через dump.
- Restore не перезаписывает каталог, проверяет каждый файл до публикации;
  повреждения, лишние/пропущенные пути, несовпадение владельца и профиля дают ошибку.
- PowerShell backup включает архив в родительский manifest. Restore сверяет
  завершённые задания из восстановленного dump до старта Gateway, сохраняет
  отчёт ошибки и убирает только собственный временный каталог.
- Исправлено поглощение `-d` advanced-функцией PowerShell в старом restore:
  аргументы Compose теперь передаются явным массивом.

## Проверки

- Go: все пакеты без production/PostgreSQL, адресные trainingagent tests, vet.
  Тесты, требующие `TEST_DATABASE_URL`, в этом прогоне пропущены.
- Windows: сборка CLI и test executable; все `TestTrainingBackup*` прошли.
  Проверены реальное архивирование/восстановление, download через API агента,
  исходный владелец, отмена, повреждение, неполный архив, snapshot при Submit,
  исключение `.partial` и сохранность существующего каталога.
- `scripts/test-training-backup.ps1`: синтаксис, корректная привязка, восемь
  несовпадений inventory и пустой набор.
- Тот же скрипт с `-TrainingBackupTool .\bin\training-backup.exe` проверяет
  настоящий Windows CLI и полные backup/restore PowerShell сценарии на
  временных fixtures. **Docker и HTTP подменены**: это проверка orchestration,
  не настоящий `pg_dump`/`pg_restore` или HTTP smoke рабочего Gateway.
- Временные fixtures удаляются; реальные конфигурации, модели, токены,
  БД, ComfyUI, Ollama, майнер и агенты не использовались и не перезапускались.

## Сквозная проверка

Следующим этапом выполнен `scripts/test-training-restore.ps1`, уже без подмены
PostgreSQL, агента и HTTP-маршрутов Gateway:

- PostgreSQL 16 на отдельном tmpfs, два новых случайно названных database.
- Настоящие `pg_dump --format=custom` и `pg_restore --exit-on-error`.
- Исходная БД и исходный файл LoRA удалены перед чтением восстановленных данных.
- Настоящий API восстановленного training-agent обслуживает Gateway client.
- HTTP-запросы идут через зарегистрированные маршруты и сохранённые сессии,
  а не через прямую подстановку `currentUser`.
- Владелец видит LoRA в `/api/lora-training/jobs` и скачивает исходные байты
  по `/train-lora/{id}/download`; чужой пользователь её не видит.
- Dataset и snapshot сохраняют trigger, ручные подписи, исключённый кадр,
  ссылку версии и hash в training job. ZIP-экспорт содержит фото и подписи.
- Кадр размером 1 771 501 байт проходит через несколько шифрованных chunks;
  после восстановления hash равен
  `c8a74e00bb6d50a1774634a22333d64d60f6cf1ce71c70c1b8c5aa1cf4fbf5da`.
- Неверный ключ, повреждённый chunk, неправильный hash snapshot и отсутствующий
  файл LoRA дают явную ошибку. Расшифрованные временные файлы удаляются.

В основной Gateway добавлена read-only команда `-verify-training-datasets`.
Штатный restore вызывает её после миграции изолированной БД: проверяются
все сохранённые наборы/версии, принадлежность изображений, AEAD и hashes.
В JSON-отчёте сохраняются числа datasets/snapshots/assets и проверенных байт.

`RESTORE_DRILL_MODE=true` применяется только в restore Compose: отключены
startup recovery заданий, bootstrap аккаунта, retention и все фоновые workers.
Адреса inference и training-agent явно замкнуты на недоступный loopback.
Собранный бинарник Gateway в тесте оставил задание `uploading` без изменений,
не изменил число аккаунтов и не сделал ни одного запроса к тестовым исполнителям.
Его CLI проверки датасетов прошёл с правильным ключом и вернул ошибку с неверным.

Сквозной тест включён в `scripts/test.ps1 -Deep`; отдельный запуск выше создаёт
и удаляет только собственный PostgreSQL-контейнер, без host-портов и GPU.

Итоговая регрессия после подключения verifier и restore-режима: полный
`go test -p 1 ./... -count=1` с отдельной PostgreSQL и включённым новым
dump/restore-тестом прошёл. `go vet` для Gateway/config/CLI также прошёл.
PowerShell-сценарий с настоящей Windows backup utility и подменёнными внешними
командами повторён после добавления dataset-verifier, без ошибок.

## Граница Готовности

Функциональная приёмка F05 выполнена локально. Согласованный выпуск Gateway,
агента со снимками профилей и Windows backup utility остаётся частью rollout.
Рабочие сервисы, реальные модели и production-БД в этих проверках не использованы.

`GatewayDownloadVerified=false` в отчёте штатного restore относится к конкретному
пользовательскому архиву: этот скрипт не подключает test-agent и не входит за
пользователя. Скачивание через Gateway доказано отдельным воспроизводимым
сквозным тестом выше, а не приписано каждому произвольному архиву.
