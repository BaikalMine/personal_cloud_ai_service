# Защита от запоздавших команд майнинга

## Область F04

HTTP-таймаут Gateway не останавливает уже выполняющийся метод Windows-agent.
Раньше после таймаута Start блокировка допуска снималась, а поздний запуск
мог пересечься с новой GPU-задачей. Простое чтение списка процессов до такого
запуска не доказывает отсутствие команды в полёте.

## Реализовано

- Миграция 67 добавляет общую PostgreSQL sequence для номеров команд.
  Рестарт Gateway и новый экземпляр store не возвращают счётчик назад.
- Протокол агента 2 содержит случайную сессию запуска и возрастающую revision.
  Старые номера, повтор того же номера и запросы из прежней сессии отклоняются
  до вызова контроллера. Смена сессии не означает завершение дочернего процесса.
- Start, Stop, Update и проверочный barrier проходят одну очередь агента.
  Barrier ожидает фактического возврата метода контроллера, а не HTTP-ответа
  клиенту. Более новый barrier запрещает запоздавший старый Start/Update.
- Ошибка изменяющей команды оставляет неподтверждённое состояние. Новый Start
  или barrier не превращает его в «свободно»; нужна успешная Stop именно того
  профиля, на котором произошла ошибка. Остановка другого профиля не подходит.
- Gateway проверяет протокол, обязательность режима, сессию, revision и наличие
  подтверждённого состояния. Нет redirect/replay и fallback на старый Start.
- Перед новым GPU-допуском проверяются все сохранённые профили майнинга,
  включая отключённые. Недоступный/несовместимый настроенный агент откладывает
  допуск. Проверка не останавливает майнер сама и не меняет пользовательскую
  политику паузы: без неё работа ждёт; обучение сохраняет обязательную паузу.
- При включённом режиме ручной Start/Update согласован с тем же admission guard,
  активной GPU-работой, mining leases и наблюдением внешних исполнителей.
  Stop остаётся доступной. Автоматический возврат последнего lease использует
  тот же нумерованный протокол; lease хранится до подтверждения результата.
- Удаление/отключение профиля также ждёт barrier. Ручной запуск повторно проверяет
  наличие и доступность профиля внутри guard, поэтому предварительно прочитанный
  удалённый профиль не может запуститься после изменения.
- В новом режиме ошибка проверки остановки не разрешает продолжать генерацию
  только с предупреждением. В старом, выключенном режиме поведение сохранено
  для согласованного выпуска, но он не считается защищённым этой реализацией.

## Проверки

- Полный Go-прогон с отдельной PostgreSQL 16 и миграцией 67 прошёл.
- Новые gateway/agent/client/config сценарии повторены десять раз.
  Проверены потерянный HTTP-ответ при продолжающемся Start, отложенный допуск,
  политика без паузы и с паузой, фактическая Stop перед inference, запрет
  ручного запуска при GPU lease и запуск по устаревшему удалённому профилю.
- Проверены задержанный Update с перезапуском, старый номер, старая сессия,
  controller error, Stop неверного профиля, старый агент, неверная revision,
  redirect, HTTP 504 и отсутствие подтверждённого состояния.
- Тест удаления сначала ошибочно использовал default-профиль, который штатно
  не удаляется. Исправлена фикстура; теперь тест проверяет факт удаления,
  а не только отсутствие SQL-ошибки. После этого десять повторов прошли.
- `go vet ./...` и Windows/amd64-сборка mining-agent прошли. Пять тестов протокола
  исполнены нативно на Windows с подменённым контроллером; реальный майнер
  и его процессы не запускались. Это не проверка Windows process-tree recovery.

## Согласованный выпуск

Изменения не включены в production. Gateway по умолчанию использует
`MINING_FENCED_COMMANDS=false`; JSON-конфигурация mining-agent по умолчанию
сохраняет `require_fenced_commands=false`.

Для будущего F14 необходимы backup, миграция 67, согласованные версии и окно
без выполняющихся/неизвестных команд. Затем агент запускается с
`require_fenced_commands=true`, Gateway с `MINING_FENCED_COMMANDS=true`.
В таком режиме агент отклоняет изменяющие маршруты `/v1/start`, `/v1/stop`,
`/v1/update`; read-only мониторинг остаётся доступным. Не включать только одну
сторону и не менять рабочие конфиги ради локальной проверки.

При откате БД нельзя вручную уменьшать sequence или считать старый номер новым.
Восстановление БД и сессии агента согласуется после подтверждения состояния
исполнявшихся команд. Сам restart не разрешает освобождение GPU.

## Что Не Закрыто

- Авария Windows-agent с launcher/дочерними процессами дополнительно проверена
  в [этапе владения процессами](MINING_PROCESS_OWNERSHIP_2026-09-06.md): Job Object,
  атомарное назначение при создании, kill-on-close и нативные тесты. Это локальная
  проверка нового режима; выпуск и приёмка с настоящим майнером ещё открыты.
- Прямой запуск пользовательского BAT вне Gateway, внешние ComfyUI/OpenWebUI
  после наблюдения, неизвестные уже отправленные модельные вызовы.
- Общая смешанная нагрузка, полный цикл отмены пакета и реальный возврат майнинга,
  эксплуатационные действия при неизвестном исходе, release/rollback/rollout.

Таким образом, проверена гонка запоздавших команд живого агента, не весь F04.
Production, установленный агент, ComfyUI, Ollama, Docker Desktop и рабочий
майнер не изменялись. UI-шаблоны и стили не менялись.
