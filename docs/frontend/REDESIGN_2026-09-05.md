# AI Gateway: новый интерфейс и две темы

Дата: 5 сентября 2026 года. База анализа: `9a1f7b1`.
Статус: дизайн-спецификация следующего цикла. Это предлагаемый интерфейс, не описание уже выпущенной версии.

Связанный документ: [аудит и функциональный план](../PRODUCT_ROADMAP_2026-09-05.md).

## 1. Направление

**Рабочая студия AI-контента.** Пользователь формулирует задачу, добавляет материалы, видит будущие параметры результата и работает с полученными изображениями/видео. Система сопровождает этот процесс, а технические настройки доступны по мере необходимости.

Визуальный характер: нейтральные поверхности, хорошо читаемые подписи, ясная сетка, крупное медиа, один основной акцент для действия. Светлая тема использует холодный белый и серый; тёмная — нейтральный графит. Мятный цвет сохраняет узнаваемость, но перестаёт окрашивать почти все блоки. Голубой означает информацию, янтарный — ожидание/предупреждение, красный — ошибку или удаление.

Сохраняем имя AI Gateway, существующие локальные шрифты, backend, права и возможности workflow. Глубина редизайна: новая информационная структура ключевых страниц и общий слой компонентов, а не косметическая перекраска.

## 2. Пользователь и задача

| Вопрос | Решение |
| --- | --- |
| Основные пользователи | Автор изображений/видео, пользователь с ограниченным доступом, автор LoRA, администратор |
| Главные объекты | Черновик, материал, генерация, результат, датасет, LoRA, пользователь, приглашение |
| Основная задача | Создать результат, оценить его и продолжить работу с ним |
| Первая развилка | Изображение, редактирование фото или видео |
| Следующий выбор | Что должно сохраниться из материалов и какое качество нужно |
| Успех | Пользователь понимает настройки и статус, получает результат, может повторить/изменить его |
| Восстановление | Сохранённый черновик, ошибка у конкретного поля, повтор после исправления |
| Mobile | Доступная основная кнопка и работа с файлами/галереей без скачивания туда-обратно |
| Основа UI | Go templates + общие CSS-компоненты + локальные JS-модули |
| Основные риски | Длинные формы, скрытая навигация, текст в каждом блоке, множество кнопок в карточках, цветовые состояния без иерархии |
| Проверка | Ключевые сценарии, обе темы, длинные данные, 390–1920 px, keyboard, zoom и экранная клавиатура |

Из основных заголовков убрать технические термины `T2VA`, `I2VA`, `FL2VA`, `REF2VA`, `workflow`, `durable job`, `lease`. Они остаются вторичной подписью, в справке или диагностике, где помогают принять решение. Названия моделей и LoRA доступны и не заменяются выдуманными обещаниями качества.

## 3. Что не работает в текущей композиции

1. На 1440 px навигация уже спрятана в меню, хотя это обычный рабочий экран.
2. Первый экран генерации тратится на заголовки, инструкции, очередь, квоты и выбор сценария; поле идеи появляется намного позже.
3. Одно решение часто объясняется заголовком, подзаголовком, карточкой, подсказкой и отдельным гайдом одновременно.
4. У галереи каждый результат обрастает несколькими рядами равноправных кнопок; визуальное содержание занимает меньшую часть карточки.
5. Обучение LoRA показывает сразу длинную подготовку набора и историю; возврат к существующей LoRA требует проходить мимо формы нового обучения.
6. Очень много текста набрано мелким полужирным шрифтом. Заголовок, статус и описание конкурируют по весу.
7. В цветах и отдельных компонентах остаются локальные исключения. Светлая тема не появится надёжно от одной смены фона.
8. Формальное отсутствие overflow не доказывает понятность режима. Screenshot-тесты должны сопровождаться проверкой пользовательской задачи.

## 4. Новая навигация

### Пользователь

Desktop: постоянная левая колонка 224 px; компактная верхняя панель 56–64 px. Главная область занимает оставшееся пространство.

```text
AI Gateway

Создать
Результаты
Задачи                         2
Мои LoRA

Инструменты
  ComfyUI
  OpenWebUI

Внизу: аккаунт / настройки
Администрирование — если разрешено
```

Пункты показываются по правам. Настройки темы, уведомлений, сессий и аккаунта находятся в одном понятном месте. Частые разделы не исчезают на 1440/1280 px. На tablet sidebar сворачивается в узкую полосу с подписанной кнопкой полного меню; на телефоне используются «Создать», «Результаты», «Задачи», «Ещё».

По умолчанию рабочий вход ведёт к созданию/продолжению черновика. Существующий `/app` остаётся совместимым маршрутом; статистика использования переходит в профиль. Открытие OpenWebUI не меняет следующий вход в Gateway.

Переключатель 18+ остаётся доступным в меню отображения медиатеки и настройках просмотра. Приоритет отражается в параметрах задачи/доступе аккаунта. Ни один из них не занимает место основной навигации в каждой мобильной шапке.

## 5. D01. Светлая, тёмная и системная темы

### Предлагаемые токены

| Роль | Светлая | Тёмная |
| --- | --- | --- |
| Фон приложения | `#F5F6F8` | `#17191D` |
| Основная поверхность | `#FFFFFF` | `#202328` |
| Вторичная поверхность | `#EEF0F3` | `#292D34` |
| Поле ввода | `#FFFFFF` | `#1B1E23` |
| Основной текст | `#20242A` | `#EEF0F4` |
| Вторичный текст | `#59616C` | `#ABB2BE` |
| Разделитель | `#DCE0E6` | `#3B414B` |
| Граница контрола | `#868F9B` | `#727D8D` |
| Основное действие | `#087F73` | `#62DDBF` |
| Текст основного действия | `#FFFFFF` | `#112721` |

Расчёт для предложенных пар: основной текст/поверхность — 15.59:1 и 13.81:1; вторичный — 6.27:1 и 7.39:1; текст основной кнопки — 4.89:1 и 9.44:1 соответственно. Это проверка конкретных пар, не сертификация всего будущего UI. Hover, disabled, selected, графики и overlay проверяются отдельно после реализации.

Имена токенов задаются по назначению: `--color-bg`, `--color-surface`, `--color-text`, `--color-text-secondary`, `--color-action`, `--color-action-text`, `--color-border-control`, `--color-focus`, `--color-danger`. Старые `--mint`/`--surface` временно становятся алиасами при миграции, затем удаляются по мере перевода потребителей. Не заводить независимую палитру для каждой страницы.

### Поведение

- Настройка «Системная / Светлая / Тёмная» с текстовой подписью и иконкой; доступна также до входа.
- Первый визит следует системной теме. Явный выбор пользователя имеет приоритет; настройка может синхронизироваться с аккаунтом.
- Нужная тема выбирается до первой отрисовки через серверное предпочтение/cookie и fallback CSS. Реализация учитывает действующую CSP.
- Смена системной темы меняет приложение только в режиме «Системная»; ручной выбор сохраняется.
- Нативные select, date и прочие controls используют соответствующий `color-scheme`.
- Изображения и видео не инвертируются и не перекрашиваются при смене темы. В просмотрщике допустима нейтральная тёмная область вокруг медиа и в светлом интерфейсе.
- Proxy-интерфейсы ComfyUI/OpenWebUI сохраняют собственные темы. Gateway не должен обещать их автоматическую синхронизацию без отдельной поддержки.
- Все состояния уведомлений, графики, редактор промпта, upload/dropzone, skeleton и диалоги поддерживают обе палитры.

Системное предпочтение определяется через [`prefers-color-scheme`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-color-scheme). Семантическое применение токенов и отсутствие глобального `filter: invert()` — проектное решение для сохранения реальных цветов контента.

## 6. D02. Типографика, сетка и компоненты

### Размеры

- Сохраняем локальный Manrope. Обычный текст: 14–15 px, вес 400–500, line-height 1.5; подписи: 13–14 px/600; заголовок страницы: 26 px/700; раздела: 18 px/650. На телефоне input/textarea: 16 px для комфортного ввода.
- 12 px используется только для второстепенных метаданных. Длинное объяснение не превращается в мелкую сноску; моноширинный шрифт нужен для seed, ID и журналов.
- Letter spacing: 0. Числа времени, очереди, квот и progress используют tabular-nums.
- Ритм отступов: 4/8/12/16/24/32 px. Между label и control 8 px; между связанными полями 16 px; между разделами 24–32 px.
- Основная высота controls: 44 px; компактные desktop-инструменты 36 px; touch target не меньше 44×44 px. Радиусы controls 6 px, media items/dialogs до 8 px.

### Сетка

- Студия: `minmax(340px, 420px)` для формы + `minmax(0, 1fr)` для результата; на узком экране одна колонка.
- Списки и медиатека используют ширину рабочей области. Формы профиля/приглашения имеют ограниченную ширину и явный итог рядом.
- Таблицы имеют выбранные по смыслу ширины, wrap для описаний и `nowrap` только для коротких состояний. Длинные email/имена доступны полностью в деталях.
- В строке полей labels, controls и hints выравниваются отдельными рядами, а не центрируются как независимые карточки. Ошибка у поля не сдвигает соседний control на случайную высоту.
- Разделы страницы не получают рамку по умолчанию. Рамка обозначает самостоятельный инструмент, повторяемый объект или диалог. Карточка внутри карточки не используется.

### Единые компоненты

`AppShell`, `PageHeader`, `Field`, `ToggleRow`, `SegmentedControl`, `Select`, `MediaSlot`, `ModelPicker`, `LoraStack`, `DisclosureSection`, `JobStatus`, `QuotaSummary`, `ResultTile`, `MediaViewer`, `Inspector`, `DataTable`, `EmptyState`, `ErrorNotice`, `ConfirmDialog`.

Названия обозначают контракты шаблонов/JS, а не необходимость устанавливать компонентный framework. Иконки взять из одного набора Lucide, локально включив только используемые. Иконке без текста нужны accessible name и tooltip; выбрать/переключить/отменить должны оставаться различимыми по форме контрола.

## 7. D03. Студия создания

### Desktop-схема

```text
┌ Навигация ┐  Создать                         Черновик сохранён    Аккаунт
│ Создать   │  [Изображение] [Редактировать фото] [Видео]
│ Результаты│  ───────────────────────────────────────────────────────────
│ Задачи    │  Идея и материалы       │ Результат / выбранная задача
│ Мои LoRA  │  [Промпт             ]  │
│           │  [Улучшить описание]    │        Изображение или видео
│           │  [Исходник] [+ реф.]    │        с корректными пропорциями
│           │                        │
│           │  Модель                │ Состояние и действия результата
│           │  Размер / длительность │ [Изменить] [Использовать] [Скачать]
│           │  ▸ LoRA                │
│           │  ▸ Постобработка       │ Последние результаты этой работы
│           │  ▸ Дополнительно       │ [медиа] [медиа] [медиа]
│           │                        │
│ Настройки │  Итог + Создать         │
└───────────┘
```

На первом посещении активен понятный базовый сценарий. Модель выбирается из разрешённых и совместимых; единственный доступный вариант не требует отдельного шага. Профиль «Быстро / Баланс / Детальнее» применяет согласованный набор, но рядом видно, что изменилось. Не использовать «Максимальное качество» как гарантию лучшего результата.

Промпт, референсы и основные параметры видны в одной рабочей области. Последняя успешная генерация остаётся рядом при настройке новой. Полная история переезжает в «Задачи», а не удлиняет форму создания на десятки экранов.

Перед основной кнопкой краткий итог: модель, базовый размер, финальный размер при обработке, число изображений или длительность/FPS, число вариантов. Ожидание очереди и остаток соответствующей квоты раскрываются по необходимости. Ошибки валидации ведут к конкретному полю.

### Режимы

| На экране | Что увидит пользователь | Технический контракт |
| --- | --- | --- |
| Изображение | Идея, модель, пропорции и размер, опции | Krea2 и другие реально доступные text-to-image recipes; без обязательного negative у Krea2 |
| Редактировать фото | Исходное фото, что изменить, дополнительные ориентиры | Krea2: до 2 фото; Flux2: до 4, по capabilities |
| Видео → По описанию и кадрам | Необязательное начало и финал, действие, камера, звук | FL2VA-ветка: без фото T2VA, одно I2VA, два FL2VA |
| Видео → По референсам | До 4 фото с ролями, опционально звук и видео | REF2VA; материалы задают признаки, не фиксируют первый/последний кадр |

Два способа видео показаны двумя простыми вариантами с одной ключевой фразой под каждым. Нельзя свести оба к неразличимому «Промпт + фото». При смене способа несовместимые материалы отмечаются и сохраняются в черновике до явного решения пользователя, но не отправляются в неподдерживаемую ветку.

### Референсы

Один слот, две команды источника: «С устройства» и «Из результатов». Не две конкурирующие большие карточки. После выбора отображаются thumbnail, имя, роль, замена и удаление. Слоты одинакового типа имеют стабильные размеры. Номер/роль видны и ассистенту, и пользователю. Preview фото целиком — по клику; crop/fit не подменяется молча.

Аудио/видео имеют собственный player и выбор используемого фрагмента. Источник звука и ожидаемая роль обозначены прямо: голос, музыкальный ориентир или звук сцены. Это не обещание точного копирования аудиодорожки.

### Опции

Постобработка оформлена вертикальными строками: название, краткий эффект, switch, раскрываемые параметры включённого модуля. Например: «Плавность движения», «Увеличить разрешение», «Согласовать цвет», «Резкость». Технический RIFE/RTX/ColorMatch виден вторично. Группа «Память и скорость» содержит SageAttention и специфичные H3-оптимизации. Турбо и пользовательские LoRA остаются опциональными в пределах совместимости модели.

Не включать скрытую тяжёлую обработку при выборе общего пресета без отображения изменения. Показывать отдельные «База 720p» и «Результат после 2×: фактические размеры».

### Mobile

Одна колонка: тип задачи → идея → материалы → основные параметры → сводка. «Настроить» и «Результат» — две вкладки внутри текущей работы, чтобы не помещать огромный результат перед формой или наоборот. Кнопка создания находится в нижней полосе с кратким итогом; при открытой клавиатуре не перекрывает поле. После отправки открывается состояние задачи. Сверху сохраняется доступ к другим задачам.

## 8. D04. Промпт-ассистент

Вход — кнопка «Улучшить описание» рядом с текстом. Режим подбирается по текущей задаче, пользователю не нужно отдельно выбирать универсальный шаблон для уже выбранного видеорежима.

Desktop: боковая панель или соседняя область, mobile: полноэкранная панель. Порядок: миниатюры и роли → что распознано → предложенный текст → действия. Подробный diff и технические сведения раскрываются отдельно. Текст «Ваш вариант» сохраняется, принятие ответа всегда явно.

Действия: «Применить», «Редактировать», «Оставить мой текст». После смены модели/режима/референсов старый ответ помечается как неактуальный. Исправление «волосы светлые» привязано к наблюдению соответствующего фото, а не требует ещё одного длинного промпта.

Для LoRA используется отдельная панель подписи кадра: изображение целиком, описание, trigger первым, перегенерация выбранного кадра и переход к следующему. Общая кнопка описывает только пустые кадры последовательно и показывает `12 из 30`, текущий кадр, ошибочные и пропущенные.

## 9. D05. Результаты и просмотрщик

Переименовать раздел в «Результаты». Основные элементы: поиск, тип, коллекция, дата, избранное и хранение. Реже используемые фильтры раскрываются в панели. Активные фильтры видны и сбрасываются одним действием.

Плитка: медиа, короткое имя/время, тип и значимый статус; прямое действие «Использовать» и меню прочих команд. Не выводить в каждую плитку полный prompt, seed, все теги и 6–8 текстовых кнопок. На touch меню доступно без hover. При выборе нескольких плиток появляется панель групповых действий.

Избранное — звезда, закрепление хранения — отдельная команда с датой. Удаление говорит, что именно исчезнет: материал, его запись или обученная LoRA; не использовать одно неясное «Убрать» для разных последствий.

Просмотрщик показывает реальное соотношение сторон, zoom/fit, соседние результаты и боковой инспектор: prompt, модель, LoRA, seed, параметры, происхождение, срок хранения. Технический паспорт раскрываемый. Сравнение A/B синхронизирует масштаб и позволяет проверить фон и мелкие детали, а не только уменьшенные лица.

«Использовать» открывает выбор назначения: редактировать фото, начало видео, финал, свободный референс, датасет LoRA. Показываются только доступные совместимые назначения. Переход переносит asset ID и роль без скачивания файла.

## 10. D06. Задачи

Отдельный раздел с типами «Все / Генерации / Обучение / Описания». Фильтры состояния, поиск и дата. Строка задачи включает название, thumbnail, состояние, последний этап, время и ближайшее действие. Детали открываются в inspector или на отдельном адресе.

| Состояние | Основной текст | Действие |
| --- | --- | --- |
| В очереди | Место и причина ожидания; оценка только если обоснована | Отменить |
| Выполняется | Реальный этап и известный progress | Открыть; отменить, если разрешено |
| Отменяется | Отмена запрошена; ждём подтверждения | Смотреть статус |
| Готово | Результат и срок хранения | Открыть / использовать |
| Ошибка | Что не удалось и что можно исправить | Исправить и повторить |
| Связь потеряна | Последнее подтверждённое состояние и countdown reconnect | Дождаться / проверить |
| Истекло | Медиа удалено по сроку хранения | Повторить с доступными параметрами |

Во время ожидания нет бегущей полосы, похожей на процент выполнения. Процент текущего этапа отличается от этапов всей задачи. Никакая ошибка соединения сама по себе не обозначает, что генерация провалилась. Скрытые окна и повторное открытие панели сохраняют scroll и выбранную задачу.

Пакет представлен одной группой с количеством готовых вариантов, настройкой эксперимента и раскрываемыми результатами. «Отменить остаток» не удаляет уже готовые изображения.

## 11. D07. Мои LoRA и обучение

Главная раздела — уже созданные LoRA и сохранённые датасеты, кнопка «Обучить LoRA». Не показывать длинную пустую форму нового обучения перед существующими результатами.

Обучение организовано в четыре понятных шага:

1. **Материал:** имя, trigger, тип концепта, сохранённый/новый датасет.
2. **Подписи:** сетка кадров, проверка, описание выбранного кадра и последовательный ассистент.
3. **Обучение:** совместимая базовая модель, понятный профиль, рабочее разрешение, дополнительные параметры и итог.
4. **Результат:** состояние run, LoRA, паспорт и проверочное сравнение.

Редактор датасета: desktop слева сетка миниатюр, справа выбранное фото и подпись. Mobile: выбранный кадр + нижняя лента и переход вперёд/назад. Состояние «Сохранено» видимо. Не смешивать подписи нескольких кадров в одном поле. Trigger фиксирован отдельным элементом начала подписи, чтобы случайно не потерять его при редактировании.

Карточка LoRA показывает понятное имя, thumbnail проверочного результата, семейство, trigger, дату, версию и состояние. Основные действия: «Использовать», «Проверить», меню со скачиванием и удалением. Создание тестового пакета показывает число запусков до отправки. Историю run и technical log открывать из LoRA, а не держать постоянно на экране.

До поддержки checkpoint UI не предлагает «Продолжить обучение». При ошибке доступны причина, сохранённый датасет и «Обучить заново»; указано удаление ошибочной записи через сутки.

## 12. D08. Пользователи и приглашения

### Пользователи

Список оптимизирован для ответа на вопросы: кто это, активен ли, временный или постоянный, что доступно, какой лимит/остаток и когда истекает аккаунт. Дата последнего входа вторична. Несколько доступов объединяются в короткую сводку с деталями, а не россыпь одинаковых pills.

Фильтры: поиск, тип аккаунта, состояние, доступ, истекает скоро. Профиль пользователя разделён на «Доступ и лимиты», «Задачи», «Активность», «Сессии». Сложное редактирование остаётся в профиле или drawer, не внутри строки таблицы.

### Приглашения

Первый выбор — шаблон доступа или своё приглашение. Далее: возможности → лимиты/ресурсы → срок ссылки и аккаунта → итог. На desktop итог находится рядом, на mobile перед кнопкой создания. Чёткие отдельные поля «Ссылка действует» и «Аккаунт будет удалён через». Не использовать `0` как единственную подсказку о безлимитном режиме: явный checkbox «Без ограничения» раскрывает/закрывает числовое поле.

В итог входят фото/видео по отдельности, базовое качество видео, приоритет, обучение, доступ к расширенным настройкам. Для изменения пользователя используется тот же компонент effective limits, чтобы не возникали разные трактовки одной квоты.

## 14. Состояния и доступность

- Loading сохраняет геометрию контента; долгие задачи показывают реальный этап и могут продолжаться после ухода со страницы.
- Empty state содержит короткую причину и одну полезную команду. Пустой список LoRA не выглядит как ошибка.
- Ошибка поля связана с ним через accessible description; общая ошибка даёт переход к первому проблемному полю. Введённые данные сохраняются.
- Disabled объясняет причину: нет доступа, исчерпан лимит, отсутствует зависимость или не хватает материалов. Не использовать одинаковое «Недоступно» для всех причин.
- Значение статуса передаётся текстом/иконкой, цвет только помогает. Фокус видим в обеих темах; sticky панели не скрывают активный элемент.
- Tooltip доступен также с клавиатуры; справка открывается по нажатию и не требует hover на телефоне.
- Dialog имеет заголовок, Escape, focus trap и возврат к исходному контролу. Drawer со сложной формой на mobile занимает экран.
- Учитываются reduced motion, увеличение до 200%, narrow width 320 px, safe-area, экранная клавиатура и iOS-поведение inputs.

WCAG 2.2 AA задаёт минимум цели указателя 24×24 px с оговорёнными исключениями; проект выбирает более удобный touch-стандарт 44×44 px. Источник: [Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). Проверка sticky/overlay должна учитывать требование, чтобы фокусируемый элемент не был полностью скрыт: [Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).

Мини-гайды сохраняются, но распределяются по моменту принятия решения: одна строка рядом с выбором режима и подробная справка по запросу. На каждом экране пользователь сначала видит текущую задачу и действие.

Первыми макетируются три самых разных экрана в двух темах: студия с результатом, медиатека и редактор датасета. Затем оформляется административный список. Это проверяет, что система подходит и творческой работе, и плотным данным, до переноса остальных страниц.

Существующие `DESIGN.md` и `FRONTEND_CONTRACT.md` обновляются при реализации D01–D02, чтобы рабочие правила соответствовали коду. Этот документ не должен становиться вторым несовместимым набором действующих правил. На мигрированной странице удаляются её старые стили, а не добавляется ещё один слой overrides.

### Матрица проверки

Основные viewports: 390×844, 768×1024, 1440×900, 1920×1080; дополнительные проверки 320 px, 1280 px и zoom 200%. Обе темы, system/light/dark preference, loading/empty/error/disabled, длинные prompts/названия/файлы, много результатов, активная очередь и потеря сети.

Playwright screenshots расширяются theme-проектами; component preview включает обе темы. Клавиатурные сценарии выполняются на desktop, критические touch-сценарии — на mobile. Chromium остаётся основной визуальной базой, Firefox/WebKit добавляются для navigation, upload, dialog, media и theme persistence.

Визуальные тесты дополняются короткой проверкой с 3–5 реальными пользователями: создать фото, превратить результат в видео, продолжить датасет, найти ошибку. Считаются время, возвраты и места, где нужна помощь. Только после этого утверждается новая эталонная композиция.

## 16. Результат дизайн-этапа

Перед внедрением всех страниц должны быть подготовлены: интерактивные макеты четырёх ключевых поверхностей, токены двух тем, состояния общих компонентов, карта маршрутов, тексты ошибок/мини-гайдов и screenshots на desktop/mobile. Сама замена цвета не считается завершённым редизайном.

Готовы спецификация и отдельный [интерактивный дизайн-концепт](prototype/index.html). В нём пять экранов: создание контента, результаты, задачи, редактор датасета LoRA и пользователи. Реализованы светлая/тёмная/system темы, адаптивная композиция, выбор референсов из результатов, независимые параметры обработки, review промпта, редактирование подписей и демонстрационные права/лимиты. Это не замена production-интерфейса и не реализация серверных пунктов F01–F15.

Макет работает как локальный HTML без сервера, учётной записи и GPU. Используются публичные демонстрационные фотографии, не пользовательские материалы. Все действия изолированы от Gateway и ComfyUI. Подробности: [README](prototype/README.md).

Проверено: синтаксис JavaScript, локальные зависимости/медиа и 9 DOM-тестов взаимодействий (`prototype/verify.cjs`). Покрыты темы, маршруты, сохранение текста, явное применение ассистента, режимы видео и активные референсы, независимость RIFE/апскейла, поиск/reuse, подписи по кадрам, пользовательские лимиты и подтверждение отмены. DOM-тесты не измеряют реальную вёрстку.

Ограничение проверки: встроенный браузер запретил открытие `file://` по своей политике. Визуальные screenshots нового макета, фактический overflow на 390/768/1440/1920 px, native keyboard/dialog поведение и cross-browser проверки не выполнены. Их нужно пройти перед утверждением и переносом дизайна. Ранее просмотренные screenshots текущего приложения не считаются проверкой этого макета.
