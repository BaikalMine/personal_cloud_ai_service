# Восстановление и restore drill

`scripts/restore.ps1` доказывает, что manifest-backed backup можно не только прочитать, но и восстановить. По умолчанию скрипт выбирает последний `backup-*.json`, проверяет размеры и SHA-256, распаковывает OpenWebUI, восстанавливает PostgreSQL, запускает текущий Gateway, применяет миграции и выполняет HTTP smoke-test.

## Безопасный запуск

```powershell
.\scripts\restore.ps1
```

Для конкретного набора:

```powershell
.\scripts\restore.ps1 -Manifest .\backups\backup-20260901-053334.json
```

Drill всегда создаёт уникальный Compose project `ai-gateway-restore-*`. PostgreSQL работает на `tmpfs`, а OpenWebUI и Gateway spool используют только временные project-scoped volumes. Публичный и административный listener получают свободные localhost-порты. В `finally` контейнеры, сеть, volumes и локальный restore-образ удаляются.

Скрипт не содержит режима записи в production и не обращается к `postgres-data` или volume рабочего OpenWebUI. `-KeepEnvironment` оставляет только изолированный проект для диагностики и печатает команду просмотра. Это не разрешение на замену production volumes.

## Что проверяется

- manifest содержит ровно один PostgreSQL dump и один архив OpenWebUI;
- размер и SHA-256 каждого файла совпадают;
- архив OpenWebUI полностью распаковывается, содержит `webui.db` и `uploads`;
- `pg_restore --exit-on-error` восстанавливает dump в пустую PostgreSQL;
- до запуска Gateway существуют пользователи и как минимум один администратор;
- после запуска история миграций непрерывна, а checksums валидны;
- число постоянных учётных записей не меняется при старте;
- фиксируются количества пользователей, временных аккаунтов, событий, медиа, настроек ComfyUI, userdata, политик доступа, майнеров и generation jobs;
- `/healthz`, `/readyz`, `/login` и административные `/metrics` работают;
- database readiness равен `true`, spool доступен `appuser` и остаётся пустым.

Отчёт `restore-drill-YYYYMMDD-HHMMSS.json` сохраняется рядом с manifest. Он не содержит секретов и включает inventory до/после миграций, возраст backup на момент проверки и фактическое время до готовности Gateway.

## Регулярность, RPO и RTO

`scripts/backup.ps1` запускает restore drill для каждого нового backup до удаления старых наборов. Если drill падает, новый архив остаётся для диагностики, а предыдущие проверенные backup не удаляются. Для аварийного быстрого снимка проверку можно явно пропустить:

```powershell
.\scripts\backup.ps1 -SkipRestoreDrill
```

Такой набор считается созданным, но не проверенным восстановлением.
При этом retention также пропускается, поэтому аварийный снимок не вытесняет
ранее проверенный набор.

- **RPO** равен возрасту последнего успешно проверенного backup. Операционная цель — не более 24 часов, поэтому backup должен запускаться ежедневно.
- **RTO** измеряется полем `RestoreToReadySeconds`. Цель для текущего объёма — не более 30 минут на том же хосте.
- `.env`, Basic Auth и другие plaintext-секреты намеренно не входят в архив. Потеря `SESSION_SECRET` делает зашифрованный AI-контент, userdata и recipes нечитаемыми, поэтому секреты должны храниться отдельно.

## Повреждение рабочей БД

1. Остановить новые записи через Gateway и зафиксировать время инцидента.
2. Не удалять повреждённый volume; создать отдельный forensic snapshot или его копию.
3. Выбрать последний manifest до момента повреждения и выполнить изолированный restore drill.
4. Сверить inventory, RPO, миграции и Gateway smoke в JSON-отчёте.
5. Создать новый production PostgreSQL volume и восстановить dump туда. Не использовать `pg_restore --clean` против рабочего volume.
6. Переключить Gateway на новую БД только после отдельного явного подтверждения администратора и повторного backup текущего состояния.
7. После переключения проверить health/readiness, вход, пользователей, приглашения, AI-контент, галерею и фоновые workers. Старый volume сохранять до окончания проверки.
