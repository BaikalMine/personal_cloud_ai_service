# Восстановление и restore drill

`scripts/restore.ps1` доказывает, что manifest-backed backup можно не только прочитать, но и восстановить. По умолчанию скрипт выбирает последний `backup-*.json`, проверяет размеры и SHA-256, распаковывает OpenWebUI, восстанавливает PostgreSQL, запускает текущий Gateway, применяет миграции и выполняет HTTP smoke-test.

## Безопасный запуск

```powershell
.\scripts\restore.ps1
```

Для конкретного набора:

```powershell
.\scripts\restore.ps1 -Manifest .\backups\backup-20260901-053334.json
```

Drill всегда создаёт уникальный Compose project `ai-gateway-restore-*`. PostgreSQL работает на `tmpfs`, а OpenWebUI и Gateway spool используют только временные project-scoped volumes. Публичный и административный listener получают свободные localhost-порты. В `finally` контейнеры, сеть, volumes и локальный restore-образ удаляются.

Скрипт не содержит режима записи в production и не обращается к `postgres-data` или volume рабочего OpenWebUI. `-KeepEnvironment` оставляет только изолированный проект для диагностики и печатает команду просмотра. Это не разрешение на замену production volumes.

## Что проверяется

- manifest содержит ровно один PostgreSQL dump, один архив OpenWebUI и, для полного training-backup, один ZIP LoRA;
- размер и SHA-256 каждого файла совпадают;
- архив OpenWebUI полностью распаковывается, содержит `webui.db` и `uploads`;
- `pg_restore --exit-on-error` восстанавливает dump в пустую PostgreSQL;
- до запуска Gateway существуют пользователи и как минимум один администратор;
- после запуска история миграций непрерывна, а checksums валидны;
- число постоянных учётных записей не меняется при старте;
- фиксируются количества пользователей, временных аккаунтов, событий, медиа, настроек ComfyUI, userdata, политик доступа, майнеров и generation jobs;
- `/healthz`, `/readyz`, `/login` и административные `/metrics` работают;
- database readiness равен `true`, spool доступен `appuser` и остаётся пустым.

## Обученные LoRA

Перед первым backup собрать Windows-утилиту:

```powershell
go build -trimpath -o .\bin\training-backup.exe .\cmd\training-backup
.\scripts\backup.ps1 -DatasetPolicy database
```

`-TrainingConfig` по умолчанию указывает на
`%ProgramData%\AI-LoRA-Training-Agent\config.json`; `-TrainingBackupTool`
позволяет выбрать другой путь к утилите. Отсутствие конфигурации или утилиты
останавливает backup до обращения к контейнерам. Для намеренно неполного
снимка существует `-SkipTrainingBackup`; это не резервная копия весов LoRA.

ZIP содержит `Trained`, завершённые записи агента, SHA-256 каждого файла,
связь с владельцем/run и снимок профиля для новых заданий. Для старых заданий
без снимка явно записывается предупреждение: текущий профиль не выдаётся за
исторический. Незавершённые `.partial`, рабочие datasets/cache/output агента,
его токен и базовые модели не копируются. Для базовых моделей сохраняется
отдельный inventory с hash, ошибками доступности и способом восстановления.
Чтение больших моделей для hash может занять заметное время.

Политика `database` включает сохранённые пользователем датасеты, версии и
подписи через PostgreSQL dump. Для расшифровки нужен исходный `SESSION_SECRET`,
который следует хранить отдельно. Это не копирование воспроизводимых кешей.

Restore сначала распаковывает LoRA в новую `.training-drill-*` рядом с backup,
проверяет все hashes и связывает артефакты с завершёнными заданиями **из
восстановленного dump до запуска workers**. Отсутствующий файл или расхождение
владельца/run/profile/имени/размера останавливает drill и сохраняет отчёт ошибки.
Одновременное удаление LoRA между dump и архивированием также обнаруживается
этой проверкой: такой набор не вытесняет предыдущий проверенный backup.

По умолчанию тестовые файлы удаляются в `finally`; `-KeepEnvironment` оставляет
их вместе с изолированным Compose-проектом. Путь записывается в отчёт.
Существующие каталоги не перезаписываются. Команда restore не переключает
боевой агент и не запускает обучение.

После запуска Gateway скрипт выполняет `/app/gateway -verify-training-datasets`
в изолированном контейнере. Команда только читает БД: расшифровывает сохранённые
manifest, проверяет hashes версий, принадлежность изображений, а затем
по одному материализует кадры с проверкой AEAD, размера и SHA-256. Подписи
не печатаются в отчёт; там только счётчики проверенных наборов, версий,
изображений и байт (`Training.DatasetIntegrity`). Ошибка останавливает drill.

Restore Compose устанавливает `RESTORE_DRILL_MODE=true`: не выполняются
автоматическое восстановление заданий, bootstrap учётки, retention и фоновые
workers. Незавершённые задания остаются в состоянии из dump. Адреса всех
исполнителей явно отключены. Это режим проверки, не рабочий режим сервера:
его нельзя переносить в production-конфигурацию. Перед настоящим переключением
нужно отдельно сверить незавершённые задания с состоянием исполнителей;
нельзя считать неизвестное выполнение завершённым только из-за восстановления БД.

`Training.Status=files_and_database_verified` относится к артефактам и БД.
`GatewayDownloadVerified=false` честно указывает, что для данного произвольного
архива скрипт не выполнял вход за владельца и HTTP-скачивание. Воспроизводимая
сквозная приёмка с настоящим PostgreSQL, сессиями и Gateway download выполняется
отдельно на синтетических данных:

```powershell
.\scripts\test-training-restore.ps1
```

Этот тест не обращается к production, создаёт PostgreSQL на tmpfs без host-порта,
удаляет исходные данные до проверки копии и убирает тестовый контейнер в `finally`.
Он также включён в `scripts/test.ps1 -Deep`.

Отчёт `restore-drill-YYYYMMDD-HHMMSS.json` сохраняется рядом с manifest. Он не содержит секретов и включает inventory до/после миграций, возраст backup на момент проверки и фактическое время до готовности Gateway.

## Регулярность, RPO и RTO

`scripts/backup.ps1` запускает restore drill для каждого нового backup до удаления старых наборов. Если drill падает, новый архив остаётся для диагностики, а предыдущие проверенные backup не удаляются. Для аварийного быстрого снимка проверку можно явно пропустить:

```powershell
.\scripts\backup.ps1 -DatasetPolicy database -SkipRestoreDrill
```

Такой набор считается созданным, но не проверенным восстановлением.
При этом retention также пропускается, поэтому аварийный снимок не вытесняет
ранее проверенный набор.

- **RPO** равен возрасту последнего успешно проверенного backup. Операционная цель — не более 24 часов, поэтому backup должен запускаться ежедневно.
- **RTO** измеряется полем `RestoreToReadySeconds`. Цель для текущего объёма — не более 30 минут на том же хосте.
- `.env`, Basic Auth и другие plaintext-секреты намеренно не входят в архив. Потеря `SESSION_SECRET` делает зашифрованный AI-контент, userdata и recipes нечитаемыми, поэтому секреты должны храниться отдельно.

## Повреждение рабочей БД

1. Остановить новые записи через Gateway и зафиксировать время инцидента.
2. Не удалять повреждённый volume; создать отдельный forensic snapshot или его копию.
3. Выбрать последний manifest до момента повреждения и выполнить изолированный restore drill.
4. Сверить inventory, RPO, миграции и Gateway smoke в JSON-отчёте.
5. Создать новый production PostgreSQL volume и восстановить dump туда. Не использовать `pg_restore --clean` против рабочего volume.
6. Переключить Gateway на новую БД только после отдельного явного подтверждения администратора и повторного backup текущего состояния.
7. После переключения проверить health/readiness, вход, пользователей, приглашения, AI-контент, галерею и фоновые workers. Старый volume сохранять до окончания проверки.
